# QA 절차 스킬

> 이 파일은 `qa-process` 스킬입니다.
> 동작 웹(프로토타입 · 시연용 웹)을 **만든 쪽과 따로** 검증하고, 그 결과를 **믿을 수 있는 QA 보고서**로 남길 때 이 파일을 먼저 읽고 따른다.
> 도메인과 관계없이 쓴다. 프로젝트별 경로 · 명령 · 링크는 프로젝트 폴더의 `planning-config.md` › 'QA' 절에서 찾는다. 이 스킬에는 고유 이름을 적지 않는다.

---

## 0. 이 스킬을 쓰는 상황

- 게시(새 버전 링크) 전후로 "얼마나 믿을 만한가"를 숫자와 근거로 답해야 할 때
- 정책 문서가 바뀌어 '정책을 시험이 얼마나 확인하나'를 다시 재야 할 때
- 개발 창이 결함을 고쳤다고 알려 와 다시 확인할 때
- 사용자가 "QA 돌려 줘", "보고서 갱신", "대조표 다시" 라고 할 때

## 1. 역할 경계 — 판정의 독립성

| | QA 창 | 개발 창 |
|---|---|---|
| 하는 일 | 점검 목록 · AI 탐색 QA · 정책 줄 대조표 · 사람 표본 확인 · 결함 목록 · 보고서 | 결함 고치기 · 회귀 시험 · 게시 · 시험 도구 고치기 |
| 고치는 파일 | QA 폴더 · QA 스크립트 · 보고서(위치는 설정 파일) | 앱 코드 · 시험 코드 · 회귀 스크립트 등 나머지 |
| 고치지 않는 것 | 앱 코드 · 시험 코드 (문제는 결함 목록과 작업 줄로) | QA 판정 · 보고서 숫자 |

- QA 창은 **코드를 읽을 수는 있지만 고치지 않는다.** 시험이 정책과 다른 동작을 맞다고 굳혀 놓은 경우도(시험 통과 ≠ 정책대로) 결함으로 올린다.
- 고칠 일은 **사용자 OK 뒤** 작업 줄에 담당 = 개발 창 이름으로 넣는다.

## 2. 순서 — 매번 이 순서로

1. **기준 고정** — 어느 게시 버전 · 코드 지문 · 정책 판을 보는지 정한다. 마지막 전체 회귀가 지금 코드와 같은지(최신성) 먼저 본다. 다르면 개발 창에 전체 회귀를 부탁하고 기다린다.
2. **재료 다시 뽑기** — 정책 줄 목록 · 시험 목록을 다시 뽑는다(명령은 설정 표). 정책 줄 key는 '절 + 줄 내용 지문'이라 줄이 끼어들어도 유지된다.
3. **정책 줄 대조표** — 장을 비슷한 줄 수로 4~6조로 나눠 AI 점검자 여러 명에게 동시에 맡긴다(지시문 §5-1). 결과를 합쳐 '정책 줄 N개 중 M개를 시험이 직접 확인'을 낸다. 점검자가 '정책과 시험이 어긋나 보임'이라고 한 줄은 **QA 창이 정책 원문 · 코드로 직접 확인한 뒤에만** 결함으로 올린다(그냥 옮기지 않는다 — 미정 질문 등으로 이미 정리된 경우가 있다).
3-1. **고친 뒤 재확인** — 개발 창이 게시를 알리면, 개발 서버가 아니라 **그 게시의 회귀가 만든 테스트 빌드**(회귀 임시 폴더의 테스트 빌드, 실행 기록의 코드 지문과 같은 것 — 위치는 설정 파일)를 복사해 미리 보기 서버로 띄워 AI 점검자 2명에게 맡긴다. 개발 창은 게시 직후 다음 작업을 시작해 개발 서버 코드가 바로 바뀐다. 결과 폴더 이름은 `<날짜>-<시각>-recheck`, 결함마다 고침 · 확인 시각을 남긴다.
4. **AI 탐색 QA** (범위를 넓힐 때) — 테스트 빌드를 켜고 같은 점검 목록을 AI 점검자 2명이 서로 모르게 확인(지시문 §5-2). 두 명 판정 일치율을 참고 지표로, 갈린 줄은 이유를 적는다.
5. **결함 목록 갱신** — 새로 찾은 것 · 다시 확인한 것을 `qa/defects.json`에(§4 규칙).
6. **보고서 만들기 · 게시** — 결론 글 파일을 새 숫자에 맞게 다시 쓰고, 보고서를 만들어 같은 링크에 올린다. 게시 버전을 주면 판 이력에 그 판이 고정된다.
7. **사람 표본 확인** — 사용자에게 보고서 '자세히 › 표본 확인'에서 맞음 · 틀림을 눌러 달라고 한다. 표시가 쌓이면 내려받아 반영하고(명령은 설정 표) 보고서를 다시 만든다.
8. **기록** — `tasks/progress.md`에 한 일, 결함 중 고칠 일은 사용자에게 물어 작업 줄로.

## 3. 판정 · 등급 기준

- **숫자는 층마다 따로** — 규칙 단위 · 화면 시나리오 · 프리패스 단계 · AI 정책 줄을 더하지 않는다. 층마다 통과 · 실패 · 해당 없음(통과율에서 뺌) · 다시 시도 통과를 따로 센다.
- **모든 숫자에 출처 표시** — 자동으로 셈(스크립트) / QA 창이 정리(AI가 판단해 쓴 글) / 사람이 표시(사용자가 직접 누른 것). AI가 쓴 글을 '사람이 정리'라고 쓰지 않는다.
- **믿음 등급**(보고서 맨 위에 늘 표시) — A = 최신성 · 통과율(실패 0) · 안정성(최근 3번 이상 실행, 다시 시도 통과 2% 이하) · 범위 넷 다, B = 통과율 + 넷 중 셋 이상, C = 그 밖. AI 판정 일치는 참고(등급에 안 넣음).
- **대조표 연결** — 직접 = 그 줄의 상황을 만들고 결과를 시험이 확인 / 일부 = 상황은 지나가지만 결과 일부만. 근거: 자동(글자 그대로 같음) · 추정(AI가 코드를 읽고 고름) · 확인(사람이 표본에서 맞다고 함). 사람이 '틀림'이라 한 연결은 뺀다.
- **AI 판정** — 통과 · 다름 · 일부만 · 확인 불가(그 상황을 만들 수 없음 — 실패 아님).

## 4. 결함 목록 규칙

- 번호 QA-001부터, 지우지 않고 상태만 바꾼다. 원본은 결함 목록 파일 하나(위치는 설정 파일).
- 칸: 제목 · 자세히(어디가 무엇과 다른지, 근거 파일 · 줄) · 정책 줄 · 종류(제품 / 시험 도구 / 정책 문서) · 심각도 · 담당(기획 / 개발) · 상태 · 찾은 곳 · 작업 줄 번호 · 이력.
- 심각도: 높음 = 정책과 다르게 동작해 판매자 · 고객이 피해 / 보통 = 정책 · 화면이 어긋나거나 시험을 막음 / 낮음 = 문구 · 표시.
- 시각: 결함마다 found(찾음: 언제 · 누가 · 어느 점검) · fixed(고침: 언제 · 누가 · 어느 게시 버전/정책 판) · verified(확인: 언제 · 어떻게)를 YYYY-MM-DD HH:mm으로 남기고, 상태를 바꿀 때마다 history에도 시각을 함께 적는다. 시각 근거는 점검 결과 파일의 끝난 시각 · 회귀 실행 기록 · 개발 창 알림의 게시 버전 — 근거가 없으면 '시각 기록 없음'으로 적고 지어내지 않는다. 보고서 결함 표에 '찾음 → 고침 → 확인'과 걸린 시간이 보인다.
- 상태: 열림 → 결정 대기(사용자 · 기획 판단) / 재현 필요 → 고치는 중(Q-번호) → 고침(개발 창 알림, 게시 버전) → 확인 끝(QA 창이 그 버전에서 다시 확인). '고침'은 개발 창 말만 믿지 않고 QA 창이 확인해야 '확인 끝'.

## 5. 점검자 지시문 (요점 — 전문은 설정 표의 기록 위치)

### 5-1. 정책 줄 대조표 점검자 (조마다 1명, general-purpose)
- 입력: 맡은 조의 정책 줄 파일 + 시험 목록(tsv). 시험 이름에서 후보를 찾고 **시험 코드를 열어 실제로 무엇을 확인하는지** 본다. 이름만 보고 연결하지 않는다.
- 세기 직접 / 일부, 해당 없으면 빈 배열(억지로 붙이지 않는다 — 빈 곳을 정확히 찾는 것이 목적). 한 줄 연결 많아야 5개, 근거 40자.
- 파일은 자기 결과 파일 하나만 쓴다, 시험은 돌리지 않는다, 모든 줄을 빠짐없이.
- 마지막 답: 줄 수 · 직접 · 일부 · 빈 줄, 빈 곳 몰린 절, 애매한 줄 3개.

### 5-2. AI 탐색 QA 점검자 (2명, general-purpose)
- **목록 밖에서 본 문제도 화면 사진을 꼭 남기게 한다.** 사진 없이 글로만 적힌 문제는 결함으로 올리기 전에 QA 창이 사진 · 재현으로 확인한다(기록과 사진이 다르면 재현해 보고, 결함이 아니면 '재현 안 됨'으로 닫음).
- 코드를 보지 않고 테스트 빌드 화면만 본다. 브라우저 세션 이름을 따로, 명령마다 시간 제한.
- 점검 목록 줄마다 직접 해 보고 통과 · 다름 · 일부만 · 확인 불가 + 확신 + 한 일 순서 + 본 것 + 화면 사진.
- 결과 JSON 형식은 지난 실행의 result.json과 같게. 실행 정보(대상 · 도구 · AI 모델 · 걸린 시간)는 meta.json에.

## 6. 보고서 구성 — 다섯 질문 순서

- 목적별 페이지 8개로 나눠 위 메뉴로 오간다(주소 끝 `#이름`으로 바로 열기): 요약(①) · 무엇을 · 어떻게(② ③) · 결함 · 할 일(④ ⑤) · 정책 대조표 · AI 점검 · 표본 확인 · 실행 기록(추이 · 판 이력) · 읽는 법. 새 구역은 `data-page`로 어느 페이지 소속인지 정한다.
- 게시 버전 보고서는 `--src`로 그 판 코드의 회귀 실행을 기준으로 잡는다 — 그 뒤 개발 중 실행은 실행 기록 추이에만 남는다.

① 믿을 만한가(결론 · 등급 · 층별 숫자 · 정책 줄 범위 · AI 정확도) → ② 어떤 기준으로 → ③ 어떻게(방법 · 환경 · 도구 버전 · 장별 범위 · 하지 않은 것) → ④ 남은 결함 · 위험 → ⑤ 앞으로 개선할 것 → 자세히(표본 확인 · 대조표 · 영역별 · 화면 대조표 · AI 탐색 · 실행 기록 · 판 이력 · 읽는 법).
- 원본 결과 파일(실행 기록 · 대조표 · 결함 · AI 결과)을 보고서와 함께 올린다.
- 결론은 한 줄 결론 + 판단 4칸(좋음 · 주의 · 문제 · 남은 일)으로 쓰고, 글 속 숫자는 {{이름}} 자리로 두어 보고서를 만들 때 자동으로 채운다(옛 숫자가 남은 결론은 틀린 보고서다). 숫자가 아닌 판단 문장은 상황이 바뀌면 다시 쓴다.
- 읽는 사람이 '이 숫자가 무엇을 센 것인지' 바로 알 수 있게, 층마다 쉬운 설명 · 예시 · 묶음별 목록을 ③ 맨 앞 '무엇을 시험했나'에 둔다. 새 시험 묶음이 생기면 보고서 스크립트의 묶음 설명표(GROUPS)에 한 줄 더한다.

## 7. 개발 창과 주고받기

- QA → 개발: 결함 번호 · 근거 · 재현 순서를 작업 줄에(사용자 OK 뒤). 실행 기록 형식을 바꾸고 싶으면 부탁만 한다(그 스크립트는 개발 창 몫).
- 개발 → QA: 작업 줄 [끝] + 게시 버전을 알림 → QA 창이 그 버전에서 다시 확인 → 결함 '확인 끝' → 보고서 갱신.
- 사용자 답은 한국어 · 쉬운 말. 3단계 이상 일은 계획 먼저.
