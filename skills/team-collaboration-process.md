# 팀 협업 프로세스 스킬 (기획 여럿 · 디자인 · 개발 · QA, AI 활용)

> 이 파일은 `team-collaboration-process` 스킬입니다.
> 기획자가 둘 이상이 되거나, 디자인 · 개발 · QA 팀이 합류해 함께 일할 때 이 파일을 먼저 읽고 따른다.
> 도메인과 관계없이 쓴다(커머스 · 예약 · 구독 · B2B 등). 프로젝트마다 다른 사람 · 담당 · 채널 · 적용 상태는 프로젝트 폴더의 `planning-config.md` › '협업' 절에서 찾는다. 이 스킬에는 고유 이름을 적지 않는다.
> 기획 단계 자체(범위 → 정책 → 기능정의서 → 화면설계 …)는 `product-planning-process`, 정책 문장은 `policy-doc-writing`, 검증은 `qa-process`를 따른다. 이 스킬은 **누가 무엇을 맡고 어떻게 주고받나**만 다룬다.

---

## 0. 언제 쓰나 — 적용 스위치

- **설정 파일 '협업' 절의 상태가 '적용 중'일 때만** 이 규칙(담당 표기 · 장 주인 · 검토 지점 · 넘김)을 실제 작업에 적용한다.
- 상태가 '시작 전'이거나 절이 없으면 참고만 한다. 혼자 일하던 방식(기존 작업 줄 · 창 규칙)을 그대로 쓰고, 이 스킬의 규칙을 문서나 작업 줄에 미리 끼워 넣지 않는다.
- 사용자가 "협업 프로세스 시작", "OO 합류", "기획 나눠서 진행" 같은 말을 하면 **8. 시작하기** 순서로 '적용 중'으로 바꾼다. 합류하는 사람이 바뀔 때도 8번을 다시 돈다.

## 1. 역할

| 역할 | 맡는 결과물 | 하지 않는 일 |
|---|---|---|
| 기획 (시니어 · 주니어) | 범위 · 정책 · 기능정의서 · **화면설계(AI로)** · 기획 ERD(논리 모델) · QA 기준표 | 디자인 시스템 원본 수정, 코드 |
| 디자인 | 디자인 시스템(변수 · 글자 스타일 · 효과 · 컴포넌트) · 디자인 가이드 | 화면 배치 · 상태 · 규칙 정하기 |
| 개발 | 개발 ERD(물리 모델) · API · 구현 | 기획 문서 직접 수정 |
| QA | 시험 케이스 · 실행 · 결함 등록 | 결함의 '기획 의도' 판정 |
| 결정권자 | 미정 질문 확정, 출시 판단 | — |

- 화면설계는 기획이 AI로 만든다. 디자인 팀은 '모양의 원본'만 맡고, 화면설계는 처음부터 그 원본(변수 · 컴포넌트)으로만 그린다(하드코딩 금지). 원본이 바뀌면 모든 화면이 함께 바뀐다.

## 2. 기획을 여럿이 나누는 법 — 도메인으로 나눈다

- **도메인(업무 영역)으로 나눈다.** 화면 주체(판매자 · 운영자 · 소비자 / 관리자 · 사용자 등)로 나누지 않는다.
  - 이유: 규칙 하나가 여러 주체의 화면에 걸친다(예: 반품 = 소비자 신청 → 판매자 승인 → 운영자 중재). 주체로 나누면 같은 규칙을 두 사람이 따로 써서 문서가 어긋난다.
  - 정책 문서 · 기능정의서 · 화면설계 페이지가 도메인 단위라 '이 장은 누구 것'이 한 줄로 정해지고, AI에게 범위를 닫아서 맡기기 쉽다.
- **도메인 주인이 그 도메인의 모든 주체 화면을 함께 맡는다.** 소비자 화면만 따로 떼어 주지 않는다.
- **위험도로 배분한다.**

  | 맡는 사람 | 고르는 기준 | 예 |
  |---|---|---|
  | 시니어 | 돈 · 법 · 개인정보, 다른 도메인과 많이 얽힌 곳, **공통 규칙 전체**(용어 · 영업일 · 알림 · 권한 공통 · 전체 지도 · 관련 문서 표) | 결제 · 주문 · 클레임 · 정산 · 계정 · 가입 심사 · 관리자 공통 |
  | 주니어 | 규칙이 비교적 닫혀 있고 화면이 많은 곳 | 상품 · 콘텐츠 · 전시 · 회원 정보 · 설정 화면 |
  | 경계 | 다른 도메인 계산에 들어가는 곳 | 배송비 · 쿠폰 등 — 처음엔 시니어, 익숙해지면 넘김 |

- **교차 규칙은 주 1회 대조한다.** 도메인을 가로지르는 규칙(예: 주문 ↔ 재고, 주문 ↔ 회원 탈퇴, 주문 ↔ 정산)을 두 주인이 함께 읽고 맞춘다.

### 새로 합류한 기획자의 순서

| 시기 | 하는 일 | 시니어가 보는 곳 |
|---|---|---|
| 1~2주 | QA · 대조 담당(`qa-process` 정책 줄 대조표, 화면설계 ↔ 기능정의서 대조). 규칙 · 도구 · 스킬을 읽으며 익힌다 | '결함 vs 의도' 판정 |
| 3~4주 | 작은 도메인 하나를 처음부터 끝까지(정책 → 기능정의서 → 화면설계 → 대조) | 정책 단계만 검토 |
| 그다음 | 맡은 도메인을 넓히고, 새 주체 화면(예: 소비자 화면) 기획이 시작되면 자기 도메인 몫까지 | 결정 · AI '판단한 곳'만 확인 |

## 3. 기획자 여럿 + AI 규칙

1. **장 주인 표:** 정책 문서 머리말에 '장 → 담당자'를 적는다. AI 창은 자기 장만 고치고, 공통 장은 시니어만 고친다. 다른 사람 장을 고쳐야 하면 작업 줄에 [보류]로 넣고 알린다.
2. **작업 줄 담당 = 사람 + 역할(+ 창):** 예) `주니어/기획`, `시니어/기획-창이름`. 창 이름은 새로 열면 바뀌므로 사람 · 역할이 먼저다.
3. **결정 권한:** 주니어도 미정 질문 · 추천안까지 쓴다. 확정 범위는 설정 파일대로(기본: 화면 · 문구 · 상태 장은 도메인 주인, 돈 · 법 · 권한은 시니어 또는 결정권자). AI가 스스로 정한 '판단한 곳'은 주니어 도메인이면 시니어가 확인한다.
4. **검토 지점 하나:** 정책을 고친 뒤 기능정의서에 쓰기 전. 기능정의서 '변경 기록'에 **작성자 칸**을 두어 누가 무엇을 바꿨는지 보이게 한다.
5. **같은 파일 동시 수정 막기:** 정책 파일 · 화면설계 파일은 고치기 전에 상대에게 알리고, 화면설계는 페이지(도메인) 단위로만 고친다. 같은 날 둘 다 고치면 버전 번호를 서로 알린다.

## 4. 디자인 팀과 일하는 법 — 시스템 · 가이드만 맡긴다

| 항목 | 기획(AI) | 디자인 |
|---|---|---|
| 화면 배치 · 상태 장 · 번호 설명 · 흐름 | 만든다 | 검토 의견(선택) |
| 변수(색 · 크기 · 간격) · 글자 스타일 · 효과 | 쓰기만 | 만들고 고친다 |
| 컴포넌트 | 쓰기만, 없는 것은 요청 | 만들고 고친다 |
| 디자인 가이드(모양 · 상호작용 · 접근성) | 따른다 | 쓴다 |
| 화면 문구 | 쓴다(문구 가이드) | 가이드 의견 |
| 사용자 화면 브랜드 · 테마 | 규칙(무엇을 고를 수 있나) | 모양 · 기본값 |

**합류 전 준비**
1. 디자인 시스템을 **별도 라이브러리 파일로 분리 · 게시**하고, 화면설계 파일은 그 라이브러리를 가져다 쓴다.
2. **토큰 대응표:** 화면설계 변수 · 글자 스타일 ↔ 코드 토큰 이름을 한 표로. 가이드가 오면 '값'만 바꾸면 되게 한다.
3. **컴포넌트 목록 · 상태표**를 인계 문서로 정리한다(`figma-component-system` 스킬).

**주고받는 순서**
1. 화면설계 중 없는 컴포넌트가 필요하면 기획이 **컴포넌트 요청**(무엇 · 어느 화면 · 상태 목록)을 낸다. 급하면 임시 컴포넌트를 그리고 이름에 `tmp/`를 붙인다.
2. 디자인이 라이브러리에 만들어 게시하고 버전을 알린다.
3. 기획(AI)이 라이브러리를 업데이트하고 `tmp/`를 교체한 뒤 검사(스타일 없는 글 0 · 기본 글꼴 0 · 겹침 0)를 돌린다.
4. 가이드가 바뀌면 디자인이 변수 값만 바꾸고, 기획은 화면이 깨지지 않았는지 점검만 한다.

## 5. 개발 · QA와 일하는 법 — 기준 문서를 넘기고, 바뀜은 한 길로

### 기준 문서 순서 (다르면 위를 따른다)

| 순서 | 문서 | 개발 · QA가 쓰는 것 |
|---|---|---|
| 1 | 정책 · 유저플로우 | 규칙 · 상태표 · 결정표 · 권한표 — 시험의 정답 |
| 2 | 기능정의서 | 기능 ID별 동작 · 예외 · 저장 데이터, 변경 기록 |
| 3 | 화면설계 | 화면 · 상태 · 번호 설명, 화면 ID ↔ 기능 ID |
| 4 | 기획 ERD(논리 모델) | 표 · 칸 · 상태값. 개발 ERD(물리)는 개발이 만들고 기획이 대조 |
| 참고 | 프로토타입(LOFI · HIFI) | 눌러 보는 시연, 규칙 파일 · 단위 시험(정답지). 제품 코드 아님 |

### 단계별 맡음 (R 만듦 · A 확정 · C 의견 · I 공유)

| 단계 | 기획 | 디자인 | 개발 | QA |
|---|---|---|---|---|
| 범위 · 1차/후속 | R/A | I | C | I |
| 정책 · 기능정의서 | R/A | I | C(가능성 · 비용) | C(시험 가능성) |
| 화면설계 | R/A | C | C | I |
| 디자인 시스템 · 가이드 | C | R/A | C(토큰) | I |
| 개발 ERD · API | C(대조) | — | R/A | I |
| 구현 | C(질문 답) | C(모양 검수) | R/A | I |
| 시험 케이스 | C(정책 줄 대조표) | — | C | R/A |
| 결함 판정(버그 vs 의도) | **A** | C(모양) | C | R |
| 출시 판단 | A(또는 결정권자) | I | C | C |

### 개발에 넘길 때 '준비 끝' (도메인 단위)
- [ ] 정책: 미정은 모두 가정값이 있고, 1차를 막는 미정은 0개이거나 가정값으로 가기로 합의
- [ ] 기능정의서: 정책과 어긋난 줄 0, 미정 번호 일치
- [ ] 화면설계: 번호 ↔ 설명 어긋남 0, 겹친 장 0, 기능정의서 '화면설계' 칸 링크 완료
- [ ] ERD: 기획 ERD 반영, 개발 ERD와 차이 목록 공유
- [ ] 킥오프: 도메인 설명(흐름 · 상태 · 예외) + 질문 목록

### 바뀜이 생길 때 — 결정 반영 고리 (한 길)
```
질문 · 결함 · 요청 → 기획이 결정(필요하면 결정 대기 목록) → 정책 → 기능정의서(변경 기록)
→ 화면설계(버전) → 화면 변경 알림 1줄 → 개발 반영 → QA 재확인 → 닫기
```
- 개발 · QA는 기획 문서를 직접 고치지 않고 **질문 · 결함으로 올린다.** 문서를 고치는 길은 기획 하나뿐이다.
- 화면 변경 알림 표의 반영 체크(정책 · 기능정의서 · 화면설계 · 개발)를 개발도 함께 본다.
- 긴급 수정은 개발이 먼저 고치되, 24시간 안에 기획이 문서에 반영한다.

### QA
- 시험 기준은 **정책 줄 대조표**(정책 문장 하나 = 시험 줄 하나). 기획이 도메인을 넘길 때 함께 준다(`qa-process`).
- 결함에는 정책 절 · 기능 ID · 화면 ID를 붙이고, 기획이 '버그 / 기획 변경 필요 / 의도대로'로 판정한다.
- 기획 쪽 시연 점검(도그푸딩)은 계속하되 제품 QA의 대체가 아니라 초기 필터로 쓴다.

## 6. AI 쓰는 법 — 사람마다 창, 규칙은 하나

| 누가 | AI로 하는 일 | 사람이 꼭 하는 일 |
|---|---|---|
| 기획 시니어 | 정책 · 기능정의서 고침, 화면설계, 대조, 일 분배 · 결정 정리 | 결정, 주니어 결과 검토, 다른 팀 조율 |
| 기획 주니어 | 자기 도메인 정책 초안 · 기능정의서 · 화면설계 · 대조 · QA 기준표 | 추천안, '판단한 곳' 표시, 검토 요청 |
| 디자인 | (선택) 컴포넌트 정리 · 토큰 대응표 | 가이드 · 모양 결정 |
| 개발 · QA | (선택) 문서 읽기 · 시험 케이스 초안 | 구현 · 검증 판단 |

- 규칙은 **스킬로 공유**한다(공유 저장소에서 받아 씀). 사람이 바뀌어도 AI가 같은 순서로 일한다.
- AI 결과는 그대로 내보내지 않는다: 시트는 미리 보기 뒤, 화면설계는 검사 뒤, 문서는 다시 읽고 확인한 뒤.
- AI가 스스로 정한 규칙은 '판단한 곳'으로 보고하고 사람이 확인한다. 결정 · 외부 공유 · 지우기는 사람이 한다.

## 8. 시작하기 (상태를 '적용 중'으로 바꿀 때)

사용자가 시작을 알리면 아래를 순서대로 하고, 끝나면 설정 파일 '협업' 절 상태를 '적용 중'으로 바꾼다. 3단계 이상이라 계획을 먼저 보여주고 OK를 받는다.

1. **사람 · 역할 확정:** 기획 시니어 · 주니어, 디자인 · 개발 · QA 합류 여부와 날짜, 결정권자.
2. **도메인 주인 표:** 2번 기준으로 배분안을 만들어 확인받고, 정책 머리말과 설정 파일에 적는다.
3. **결정 권한 범위:** 주니어가 확정할 수 있는 것 / 시니어 · 결정권자가 확정할 것.
4. **도구 준비:** 기능정의서 '변경 기록'에 작성자 칸, 작업 줄 담당 표기를 '사람/역할'로, 스킬 공유 저장소 접근 권한.
5. **디자인 합류 시:** 4번 '합류 전 준비' 3가지.
6. **개발 · QA 합류 시:** 도메인별 '준비 끝' 점검 → 킥오프 일정, 정책 줄 대조표 전달.
7. **작성 규칙 공유:** 개인 메모리에만 있는 프로젝트 규칙 · 결정이 없는지 확인하고, 있으면 공통 스킬(고유 이름 없이) · 설정 파일 · 정책 문서로 옮긴다. 스킬은 공유 저장소 한 곳을 원본으로 둔다.
8. 설정 파일 갱신 · 진행 기록 남기기.

## 9. 작업 줄 · 기록 (여러 AI 창이 함께 일할 때)

- **작업 줄**(프로젝트의 queue 파일): `- [대기] Q-번호 | 담당: 사람/역할(+창) | 할 일: … | OK: 사용자 날짜 "말" | 근거: …`. 상태 [대기] → [진행 중] → [끝] / 막히면 [보류]. 줄은 지우지 않고 상태만 바꾼다. 사용자 OK가 없거나 다른 담당 부탁만 있으면 [보류]. 번호는 끝난 줄 파일과 합쳐 마지막 + 1.
- 끝난 줄은 따로 모아 작업 줄 파일을 짧게 유지한다.
- **할 일 목록 체크는 내 섹션만**(내 제목부터 다음 제목 전까지). 다른 창이 같은 파일에 섹션을 덧붙인다.
- 창 대화가 길어지면(대략 20%) 넘김 메모를 쓰고 새 창으로. 큰 파일 · 긴 기록은 필요한 줄만 읽고, 넓게 찾을 일은 도우미에게 맡긴다.
- 창 이름은 새로 열면 바뀐다. 기억에 기대지 말고 매번 확인하고, 담당은 사람 · 역할로 적는다.
- 결정으로 화면이 바뀌면 '화면 변경 알림' 표에 한 줄: 화면/기능 ID · 기능명 · 변경 전 · 변경 후 · 화면 링크 · 날짜 + 반영 체크(기능정의서 · 정책 · 화면설계 · 개발 · 담당 확인).
