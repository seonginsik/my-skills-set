# 기획 프로세스 스킬 (범위 → 정책 · 유저플로우 → 기능정의 → LOFI 프로토타입 → 화면설계 → HIFI 프로토타입)

> 이 파일은 `product-planning-process` 스킬입니다.
> 서비스의 영역(기능 묶음)을 새로 기획하거나, 결정된 사항을 여러 결과물에 반영하거나, 담당 간에 일을 넘기고 대조할 때 이 파일을 먼저 읽고 따른다.
> 도메인과 관계없이 쓴다. 프로젝트마다 다른 경로 · 도구 · 명령 · 링크는 프로젝트 폴더의 `planning-config.md` › '기획 프로세스' 절에서 찾는다. 이 스킬에는 고유 이름을 적지 않는다.

---

## 0. 이 스킬을 쓰는 상황

- 새 영역(예: 가입, 주문, 정산, 회원, 관리자 화면)을 기획할 때 — "앞서 했던 방식처럼"이라는 말도 여기에 해당
- 결정 하나(기능 넣기·빼기, 미정 확정)를 기능정의서 · 정책 문서 · 화면설계서 · 동작 웹에 퍼뜨릴 때
- 다른 담당(화면설계 · 개발 — 사람이든 다른 작업 창이든)에게 일을 넘기거나, 넘겨받은 결과를 대조할 때

같이 쓰는 스킬:
- 정책 문장을 쓰거나 다듬을 때 → `skills/policy-doc-writing.md`
- 기능정의서 쓰는 법 → `spec-sheet-writing` · 화면설계 쓰는 법 → `screen-spec-writing` · 화면 문구 → `ux-writing`
- 지표 개선 프로젝트(전환율 등) 설계 → `skills/pm-feature-workflow.md` (그 3단계 PRD 뒤에 이 프로세스로 이어진다)
- 기획자 여럿 · 디자인 · 개발 · QA 팀과 나눠 일할 때(누가 무엇을 · 넘김 기준) → `skills/team-collaboration-process.md` (프로젝트 상태가 '적용 중'일 때만)

## 1. 다섯 단계 (범위를 정한 뒤 순서대로, 건너뛰지 않는다)

| 단계 | 결과물 | 묻는 것 |
|---|---|---|
| 0 범위 | 메뉴구조 · IA (1차 / 후속) | 어디까지 만드나? |
| 1 정책 · 유저플로우 | 공유 페이지 1개 (전 영역) — **규칙의 기준** | 어떤 규칙으로, 어떤 순서로? |
| 2 기능정의서 | 클라우드 시트 1개(전 영역, 기능정의 + 미정만) | 화면 · 기능마다 무엇을 하나? |
| 3 LOFI 프로토타입 | 디자인 없는 단일 HTML | 규칙대로 정말 돌아가나? |
| 4 화면설계서 | 피그마, 영역별 페이지 | 화면 어디에 무엇이? |
| 5 HIFI 프로토타입 | 웹 링크 2개(검토용 · 테스트용) | 영역을 이어 붙여도 맞나? |

- 문서끼리 다르면 정책 · 유저플로우 → 기능정의서 → 화면설계서 → 동작 웹 순서로 따른다.
- 단계마다 사용자 확인을 받고 다음으로 넘어간다. 견본 1장(또는 1영역)을 먼저 보여주고 OK를 받은 뒤 대량 작업한다.
- 3~5단계는 사용자가 요청할 때만 한다. "프로토타입" · "LOFI" = 3단계 단일 HTML, "동작 웹에" · "HIFI" = 5단계. 헷갈리면 묻는다.
- 프로젝트가 작으면 4 · 5단계는 생략할 수 있다(사용자에게 확인).

### 0단계. 범위
- 메뉴구조(대메뉴 › 중메뉴)와 1차 / 후속을 먼저 정한다. 회사 원본 요구사항이 있으면 그 메뉴를 출발점으로 쓴다.
- **끝난 때:** 메뉴마다 1차 / 후속이 정해져 있을 때.

### 1단계. 정책 · 유저플로우 (규칙의 기준)
- 전 영역을 **한 파일**에서 관리한다. 영역마다 같은 틀:
  요약 · 등장인물 → 꼭 알아둘 것 3~5줄 → 흐름 그림(정상 흐름만) → '이럴 때 | 이렇게 돼요' 표 → 상태 · 권한 · 결정표 → 미정 질문 → 이어지는 영역.
- 머리말에 범위, 기준 문서, 표시의 뜻을 적는다. 맨 앞 '전체 지도'(영역이 이어지는 순서 · 등장인물 · 용어 · 그림 읽는 법).
- 본문에 버전 · 기능 ID · 출처 표시 금지. 표시는 '미정 · 번호'와 '후속'만. 기능 ID는 맨 끝 '관련 문서'에만.
- 흐름 그림은 Mermaid. 여러 주체가 주고받으면 sequenceDiagram, 상태는 stateDiagram. 칸 글자를 "1. "처럼 숫자+점으로 시작하지 않는다. 문법과 그리기 둘 다 검사한다.
- 공유용 HTML을 만들어 같은 링크에 다시 게시한다.
- 유저플로우로 필요한 화면 · 기능이 정해진다. 2단계 기능정의서는 이 흐름과 규칙을 기준으로 쓴다.
- **끝난 때:** 그림 오류 0, 미정 질문마다 가정값이 있을 때.

### 2단계. 기능정의서 (정책을 화면 · 기능 줄로 내리기)
- 1단계 정책 문서의 규칙을 기능 줄의 동작 · 예외 칸으로 내린다. **규칙을 기능정의서에서 새로 만들지 않는다** — 새 규칙이 필요하면 정책 문서에 먼저 쓰고 내려온다.
- 회사 원본은 고치지 않는다. 새 파일에 원본과 같은 열 구성으로 옮긴다. 원본이 없으면 기능 ID · 메뉴 · 기능 · 설명 · 규칙 · 예외 · 1차/후속 열로 시작한다.
- 기능정의서에는 **기능정의와 미정 질문만** 둔다. 상태표 · 결정표(숫자 예시) · 변경 대조표 · 변경 이력은 1단계 정책 문서에 둔다.
- 줄 색 · 고치는 법(고칠 줄만 · 미리 보기) · 셀 메모와 변경 기록 기준 · 범위에서 뺄 때(후속 고려 탭) · 화면설계 링크 · 미정 관리는 `spec-sheet-writing` 스킬을 따른다(엑셀 · 구글 시트 · 노션 데이터베이스 모두).
- 법정 기준(해당 업종 법, 개인정보 보호법 등), 예외, 동시 처리, 기한을 시니어 기획자 수준으로 채운다.
- **끝난 때:** 운영정책과 어긋나는 기능 줄 0, 결정된 미정은 목록과 본문에서 지워져 있을 때.

### 3단계. LOFI 프로토타입 (디자인 없는 단일 HTML)

> LOFI(저충실도): 디자인 없이 기능 흐름과 규칙만 확인하는 HTML 한 장. 영역 하나씩, 규칙 패널 · 예외 스위치 · 가상 시간으로 정책을 눌러 본다. 시각 디자인과 영역 간 연결은 다루지 않는다.
- 왼쪽 화면, 오른쪽 규칙 패널(지금 걸린 규칙과 기능 ID · 예외 스위치 · 기록).
- 가상 시간 버튼(기한 규칙 확인), '유저 플로우 대조'(지금 단계 노란 띠, 지나온 단계 진하게, 안 간 단계 흐리게).
- 단계 바로 가기 · 프리패스(실제 규칙을 거쳐 자동 통과, '실패로 통과' 포함)를 처음부터 넣고, 테스트용에서만 보이게 한다.
- 영역 간 연결(예: 주문 → 재고)은 가상 버튼으로 실제 동작하게 보여준다.
- **끝난 때:** 시나리오 자동 클릭 점검(정상 + 예외) 모두 통과 후 비공개 게시.

### 4단계. 화면설계서 (피그마)
- 한 장 = 머리글(화면 ID · 경로 · 기능 ID) + 화면 + 오른쪽 설명(상태 칩 · 번호 항목 · 미정 Q).
- 영역(메뉴)별 페이지. 페이지 맨 위 '목록 · 상태표' 구역, 맨 아래 보관 구역. 페이지 간 이동은 링크 표시 컴포넌트로(피그마는 페이지 간 클릭 연결 불가).
- 구역은 메뉴 순서로, 구역 안은 화면 하나 = 한 줄(사용 순서: 목록 → 등록 → 상세 → 수정), 상태 a→z.
- 번호는 화면 읽는 순서, 같은 화면의 모든 상태 장에서 같은 번호. 상태 장 설명은 보이는 것만.
- 색 · 글자 · 버튼은 변수 · 텍스트 스타일 · 컴포넌트로만(하드코딩 금지 — 디자인 가이드가 바뀌어도 원본만 고치면 되게).
- 머리글 칸 · 번호 규칙 · 배치 간격 · 입력 폼 배지 · 보관 · 대응표 · 만들 때 함정은 `screen-spec-writing` 스킬을 따른다.
- **끝난 때:** 번호 ↔ 설명 어긋남 0, 겹친 장 0.

### (선택) 기획 ERD — 논리 모델
- 기획 · 디자인이 읽는 데이터 모델. 원본 데이터 파일 하나에서 공유 페이지 · 엑셀을 만든다(만든 결과물을 직접 고치지 않는다).
- 표 · 칸은 한글 이름이 먼저, 칸마다 근거 기능 ID. 결정에 따라 표 · 관계가 바뀌는 미정은 '구조 미정' 표시, 값만 바뀌는 미정은 칸에만.
- 정책 · 기능정의서가 바뀌면(기능 빼기 · 미정 확정) 원본을 고치고 다시 만들어 같은 링크에 올린다. 개발 ERD(물리 모델)와의 차이는 도메인을 넘길 때마다 대조한다.

### 5단계. HIFI 프로토타입 (동작 웹)

> HIFI(고충실도): 화면설계서의 화면 구성 · 문구를 반영하고 여러 영역을 하나의 웹으로 이어 붙여 실제 서비스처럼 눌러 보는 동작 웹. 데이터는 가짜(모의 서버), 검토용 · 테스트용 두 링크.
- 화면 → 서버 창구 → 가짜 서버로 나누고, 규칙은 한 파일에 모아 단위 시험으로 지킨다(나중 실제 서버의 정답지).
- 영역은 모듈로 붙인다. 새 모듈은 자기 파일만 채우고, 공용 파일은 고치기 전에 다른 담당에게 알린다.
- 검토용(테스트 도구 없음) · 테스트용(바로 가기 · 프리패스만 추가) 두 링크는 같은 소스에서 연달아 빌드해 함께 올린다.
- 개발 중엔 바뀐 곳만 회귀 점검, 게시 전엔 전체 회귀 점검.
- 화면 옆 '설계 보기' 번호는 피그마 번호와 같게.
- **끝난 때:** 전체 회귀 통과 → 두 링크 게시 → 기획 쪽 문서 대조.

## 2. 결정 반영 고리

```
미정 질문 → 결정(누가 · 언제) → 정책 문서 먼저 → 기능정의서 → 화면설계 · 웹(담당에게 넘김) → 대조 → 미정 목록에서 지우고 마감
```

1. 결정은 사용자(또는 결정권자)에게 받는다. 추측으로 확정하지 않는다.
2. 정책 문서를 먼저 고친다(규칙의 기준).
3. 기능정의서 시트에서 영향받는 줄만 고치고, 미정 표를 정책 문서와 맞춘다(권한표 · 상태표 · 결정표는 2번 정책 문서에서 이미 고침).
4. 화면설계 · 개발 담당에게 아래 '넘김 메모'로 보낸다.
5. 반영이 끝나면 넘긴 쪽이 원래 문서와 대조한다(예: 뺀 기능 이름 검색 0건).
6. 결정된 미정은 미정 질문 목록과 본문에서 지운다.

뺀 기능은 본문(장 설명 · 시연 문구 · 화면 목록)에 '1차 제외/없음'으로 남기지 않는다. 흔적은 보관 구역과 기능정의서 변경 이력에만. 피그마에는 변경 이력을 두지 않는다(버전 번호만).

## 3. 문서끼리 다를 때 기준

1. 정책 · 유저플로우 문서 — 규칙 · 일하는 순서
2. 기능정의서 — 화면 · 기능 세부
3. 화면설계서 — 배치 · 상태별 모양 · 번호 설명
4. HIFI · LOFI 프로토타입 — 따라가는 쪽. 문서와 다르면 웹을 고친다.

프로젝트 시작 때 이 순서를 사용자와 확인하고 정책 문서 머리말에 적는다. 사용자가 준 파일 · 링크가 기준이다.

## 4. 협업 규칙

| 담당 | 맡는 결과물 | 넘기는 것 |
|---|---|---|
| 기획 | 기능정의서 · 정책 문서 · LOFI 프로토타입 | 바뀐 규칙과 고칠 곳 목록 |
| 화면설계 | 화면설계서 · 컴포넌트 | 바뀐 장 목록, 번호 대응표 |
| 개발 | 동작 웹 · 자동 점검 | 점검 결과, 게시한 버전 |
| 결정권자 | 미정 질문 결정 | 결정과 날짜 |

- 같은 파일을 여럿이 고칠 때: 고치기 전에 알린다(ListAgents로 다른 창 확인), 내 구역만 고친다, 구역 크기가 바뀌면 아래를 같은 거리로 민다, 마지막에 겹침 검사.
- 할 일 목록 체크는 내 섹션만.
- 링크 게시 순서를 맞추고, 내 변경이 이미 들어간 빌드면 다시 올리지 않는다.
- 완료는 직접 돌려 본 뒤에만 말한다.
- 화면 문구는 프로젝트의 문구 가이드(말투 · 용어)를 따른다.

### AI 작업 창으로 돌릴 때
> 자세한 AI 작업 방식 문서는 내부용으로 따로 둔다(위치는 설정 파일). 공유용 '기획 프로세스' 페이지에는 AI 내용과 ERD를 넣지 않는다.
- 작업 창 넷: 조율(일 나누기 · 결정 질문 모으기) · 기획(기능정의서 · 정책 · LOFI) · 피그마(화면설계서) · 개발(HIFI · ERD). 창끼리는 메시지(SendMessage)로 새 파일 목록 · 바뀐 데이터 칸 · 고칠 곳을 넘기고, 받은 창은 반영 계획을 답한다.
- 여러 문서 일괄 수정은 도우미(서브에이전트)에게 지시서로 맡긴다: 기준 문서 · 사용자 결정 · 파일 규칙 · 끝난 뒤 검사 · 보고 형식(바꾼 행 · '판단한 곳'). 결과는 넘긴 쪽이 다시 검사하고, 틀리면 다시 시킨다.
- AI가 스스로 정한 규칙은 '판단한 곳'으로 사용자에게 보고해 확인받는다. 결정 · 견본 OK · 외부 업로드 · 지우기는 사람이 한다.
- 결정으로 화면이 바뀌면 '화면 변경 알림' 표(위치는 설정 파일)에 한 줄(반영 체크 4칸)을 남긴다.

### 넘김 메모 틀

```
[무엇이 바뀌었나]
[왜 · 언제] (결정 날짜, 정책 문서 반영 위치)

[확인 방법]
[끝나면 알려줄 것] 바뀐 장 목록, 게시한 버전
```

## 5. 기록

- 작업 시작: `tasks/todo.md`에서 내 항목 확인. 3단계 이상이면 계획을 먼저 적고 OK 받기.
- 작업 끝: `tasks/progress.md`에 날짜별로 덧붙이기. 지난 기록은 고치지 않는다.
- 결정을 기다리는 일은 따로 모아 주간보고(기획팀 주간보고 형식)에 올린다.
- 외부에 올리기 전 민감정보(연락처 · 사업 수치 · 대외비 원본) 확인.

## 6. 새 프로젝트에 처음 적용할 때
