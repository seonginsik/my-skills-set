# 운영정책·비즈니스 로직 정리 스킬

> 이 파일은 `policy-doc-writing` 스킬입니다.
> 어떤 서비스든 **운영정책(비즈니스 규칙·비즈니스 로직)** 을 새로 정리하거나, 이미 있는 정책 문서를 다듬을 때 이 파일을 먼저 읽고 따른다.
> 커머스·예약·구독·마켓플레이스·B2B SaaS 등 도메인과 관계없이 쓴다. 예시는 이해를 돕는 가상의 것이다.

---

## 0. 이 스킬을 쓰는 상황

- 새 서비스·기능의 운영정책을 처음 정리할 때
- 정책 문서가 "너무 세부적이다 / 이해하기 어렵다 / 순서가 이상하다 / 빠진 게 있는 것 같다"는 요청을 받았을 때
- 기능을 범위에서 넣거나 빼서 정책을 함께 고쳐야 할 때
- 기능명세·화면설계·데이터 정의와 정책 문서의 경계를 정해야 할 때

---

## 1. 먼저 구분한다 — 정책(비즈니스 규칙)과 기능명세

| | 정책 (비즈니스 규칙) | 기능명세 (요구사항·화면) |
|---|---|---|
| 답하는 질문 | **무엇이 항상 지켜져야 하나** | 시스템이 **그것을 어떻게** 해 주나 |
| 바뀌는 이유 | 사업·법·운영 방침이 바뀔 때 | 화면·기술·구현이 바뀔 때 |
| 예 | "결제 후 7일이 지나면 환불할 수 없다" | "주문 상세에 환불 버튼을 두고, 7일이 지나면 비활성화한다" |

- **판별 질문:** 시스템을 통째로 새로 만들어도 그대로 지켜야 하는 문장이면 정책이다. 화면이나 구현이 바뀌면 같이 바뀌는 문장이면 기능명세다.
- 기능 요구사항은 정책에서 나온다. 정책을 먼저 정하고, 기능명세는 정책 번호를 가리킨다.
- 정책 문서와 기능명세가 따로 있으면, **둘이 다를 때 어느 쪽을 기준으로 할지** 프로젝트 시작 때 정해 머리말에 적는다.

## 2. 규칙의 종류 — 무엇을 빠짐없이 정해야 하나

규칙은 아래 유형으로 나눠 생각하면 빠진 게 잘 보인다. 문서에 유형 이름을 붙일 필요는 없다. 정리할 때 점검용으로 쓴다.

| 유형 | 뜻 | 예 |
|---|---|---|
| **용어·사실** | 말의 뜻, 무엇과 무엇이 어떤 관계인가 | "주문 1건은 한 번의 결제로 산 상품 묶음이다" |
| **제약 (막음)** | 조건을 어기면 처리를 막는다 | "재고가 0이면 결제할 수 없다" |
| **가이드라인 (경고)** | 막지는 않고 경고만 한다 | "같은 송장번호를 다시 쓰면 경고하지만 저장은 된다" |
| **자동 처리 (행동 유발)** | 조건이 되면 다른 일이 일어난다 | "배송완료 7일 후 자동으로 구매확정한다" |
| **계산** | 값을 어떻게 계산하나 | "환불액 = 결제액 − 반품 배송비" |
| **판정 (추론)** | 조건을 보고 상태·자격을 판단한다 | "최근 3개월 구매액이 30만 원 이상이면 VIP다" |
| **권한** | 누가 무엇을 할 수 있나 | "판매자는 자기 몰 주문만 볼 수 있다" |

## 3. 정책 문서의 기본 뼈대

### 머리말 (반드시)
- 이 문서가 다루는 범위와 다루지 않는 범위 (화면 세부·데이터 형식은 어디에 있는지)
- 다른 문서와 다를 때의 기준 문서
- 본문에 쓰는 표시의 뜻 (아래 7절)
- "예:"는 가상의 예시라는 안내

### 목차는 중요도 순
**돈 → 법·개인정보 → 핵심 거래 흐름 → 예외·사고 → 운영·관리(관리자·제재) → 계정 → 등록·설정** 순서로 놓는다. 사고가 나면 비용이 큰 것부터 읽히게 한다.

### 정책 항목 하나의 모양
```
## P-n. 정책 이름
- **규칙 한 문장 (굵게)** — 누가 / 언제(조건) / 무엇을 해야 하거나 할 수 없나
	- 예: 숫자가 들어간 구체적인 상황 한두 줄
	- (필요하면) 이유: 왜 이렇게 하나
- 예외: 이 규칙이 적용되지 않는 경우
- 미정: 아직 정하지 않은 값 (가정값 함께) · 질문 번호
```

## 4. 규칙 문장 쓰는 법

1. **한 문장에 규칙 하나.** "A이고 B이며 C일 때는 D" 처럼 길어지면 나눈다.
2. **선언형으로 쓴다.** "~해야 한다 / ~할 수 없다 / ~이면 ~이다". 화면 동작 순서("버튼을 누르면 팝업이 뜨고…")로 쓰지 않는다.
3. **주어를 밝힌다.** 구매자인지, 판매자인지, 관리자인지, 시스템(자동)인지.
4. **조건과 기한은 숫자로 쓴다.** "적절한 기간", "빠르게", "일정 금액"은 쓰지 않는다. 숫자가 미정이면 가정값을 적고 미정 표시를 단다.
5. **용어를 하나로 통일한다.** 같은 대상을 여러 이름으로 부르지 않는다. 용어집(개념 문서)과 같은 말을 쓴다.
6. **전문 용어는 처음 나올 때 풀어 쓴다.**
   - 예: PG(카드 결제대행사), 귀책(누구 탓인지), 스냅샷(주문 당시 정보 보관)
7. **조건이 두 개 이상 얽히면 결정표로 쓴다.**
   - 예: 반품 사유 × 무료배송 여부 → 누가 배송비를 내나

   | 반품 사유 | 처음에 무료배송이었나 | 환불액 |
   |---|---|---|
   | 단순 변심 | 예 | 결제액 − 반품 배송비 − 면제받은 배송비 |
   | 단순 변심 | 아니오 | 결제액 − 반품 배송비 |
   | 불량·오배송 | 상관없음 | 결제액 전액 |

## 5. 정책에 남길 것 / 뺄 것

| 남긴다 (규칙) | 뺀다 (기능명세·화면·데이터 세부) |
|---|---|
| 권한: 누가 무엇을 할 수 있나 | 화면 문구, 버튼 위치, 안내 메시지 |
| 돈: 결제·환불·정산 계산, 누가 비용을 내나 | 입력 항목 목록, 글자 수·형식 규칙 |
| 상태가 바뀌는 조건, 자동 처리 기한 | 번호 형식(주문번호 등), 코드값 |
| 법·개인정보 원칙 (보관, 가림, 동의 기록) | 필터·정렬 항목, 목록에 보여줄 칸 |
| 예외·사고 처리 원칙 | 처리 단계별 화면 흐름 |
| 바꾸기 어려운 구조 결정 (+ 이유) | 기술 방식 (API, 테이블 구조) |

- 뺀 세부는 버리지 않는다. 데이터 형식은 데이터 정의 문서로, 화면 세부는 기능명세·화면설계로 옮긴다. 아직 갈 곳이 없으면 정책 문서 맨 아래 접기 목록에 "화면 설계 때 정할 것"으로 한 줄씩 남긴다.
- 다른 문서의 번호(기능 ID 등)는 본문 곳곳에 쓰지 않는다. 맨 아래 "관련 문서에서 볼 곳" 표 한 곳에 모은다.

## 6. 예시 다는 법

**예시가 필요한 것**
- 추상적인 개념, 구조 결정
  - 예: "주문은 배송 묶음 단위로 나눈다" 같은 말은 상자 2개 예시가 있어야 이해된다.
- 계산 규칙: 환불액, 수수료, 무료배송 기준
- 기간 규칙: "N일 후 자동 ○○"
- 예외: 자격 만료, 계정 정지, 분실, 품절, 결제 중 이탈

**쓰는 법**
- 규칙 바로 아래에 들여쓰기로 `- 예:` 한두 줄
- 가상의 이름과 **구체적인 숫자**를 쓰고, 계산은 식으로 보여준다.
  - 예: "32,000원 − 3,000원 − 3,000원 = 26,000원 환불"
- 날짜 예시는 실제 달력의 요일을 확인한다 (영업일 계산).
- 쉬운 규칙에는 달지 않는다.

## 7. 표시는 최소한으로

- 본문 표시는 두 가지만 쓴다.
  - **미정 · Q번호** — 아직 정하지 않았다. 가정값을 함께 적는다.
  - **1차 / 후속** — 이번에 만드는지, 나중에 만드는지
- **출처 표시를 쓰지 않는다.** "새 제안", "기존 시스템 규칙", "원문 p.3", "회의에서 결정" 같은 표시는 처음 보는 사람이 구분할 수 없다. 출처가 필요하면 변경 이력이나 별도 대조표에 둔다.
- 처음 쓰는 표시는 머리말에 뜻을 적는다.

## 8. 빠지기 쉬운 정책 점검표 (도메인 공통)

정책을 처음 정리할 때 아래 주제마다 "정했는가 / 해당 없음 / 미정"을 확인한다.

- **계정·인증:** 가입 조건(나이·본인 확인), 로그인 실패 잠금, 자동 로그아웃, 탈퇴와 탈퇴 후 데이터, 휴면
- **권한:** 역할별로 볼 수 있는 것·할 수 있는 것, 관리자 권한, 대리 처리
- **돈:** 가격 결정, 할인·쿠폰·포인트, 결제수단, 부분 결제, 환불 계산, 수수료·정산, 세금·영수증
- **수량·한도:** 재고, 1인 구매 한도, 예약 정원, 동시에 같은 것을 사려 할 때
- **상태와 기한:** 상태 목록, 바뀌는 조건, 자동 처리 기한, 되돌릴 수 있는가
- **취소·변경·반품:** 언제까지 누가 할 수 있나, 승인이 필요한가, 비용은 누가 내나
- **예외·사고:** 외부 연동 실패, 결제 중 이탈, 지연, 분실, 부정 이용, 분쟁
- **과거 기록:** 원본이 바뀌어도 지난 거래는 당시 값으로 남기나 (스냅샷)
- **개인정보·법:** 수집·보관 기간, 화면에서 가리는 범위, 동의 기록, 접근 기록, 업종별 법정 표시
- **제재·운영:** 경고·정지·해제 조건, 정지 중 진행 중인 거래 처리
- **안내 수단:** 알림이 없거나 범위 밖이면 사용자가 상태를 어디서 확인하나

## 9. 미정 사항 관리

- 회사가 정해야 할 질문은 **질문 목록 한 곳**에서 번호를 붙여 관리한다. 본문에는 "미정 · Q번호"와 가정값만 적는다.
- 질문마다 적는 것: 1차를 막는 정도(🔴 막음 / 🟠 개발 중 필요 / 🟢 후속), 확인할 부서, 상태(미확인·확인 중·결정됨)
- 결정되면 질문을 "결정됨"으로 바꾸고 근거를 적은 뒤, 본문의 미정 표시를 지우고 결정된 값으로 고친다.

## 10. 바꿀 때의 규칙

- **범위를 바꾸면 파급을 함께 고친다.** 기능을 빼면 그 기능을 전제로 한 문장을 모두 지운다.
  - 예: 알림을 빼면 "○○하면 알린다"를 지운다. **대신 사용자가 어디서 확인하는지**(주문 내역 등)도 정책으로 정한다.
- **번호를 다시 매기는 것은 피한다.** 새 내용은 가까운 절의 하위 절로 넣는다. 꼭 다시 매기면 모든 문서의 참조를 한 번에 바꾼다.
- **고치기 전에 문서를 다시 읽는다.** 다른 사람이 직접 고친 부분은 되돌리지 않는다.
- 고친 뒤 다시 읽어 확인하고, 변경 이력에 한 줄 남긴다.
- 대외비 원본 자료는 문장을 그대로 옮기지 않고 요약한다. 작성자 이름은 쓰지 않는다.

## 11. 정책을 한 파일 · 공유 페이지로 관리할 때

- **전 영역을 한 파일**에 둔다. 영역별 파일로 나누면 버전이 뒤처진다. 이 파일이 규칙의 기준이고, 다른 문서(기능정의서 · 회의록 등)와 다르면 이 파일을 따른다.
- 영역마다 같은 틀: 요약 · 등장인물 → **꼭 알아둘 것 3~5줄 + 운영 기준 표**(기한 · 횟수 · 한도 같은 정해진 값을 모음) → 흐름 그림(정상 흐름만) → '이럴 때 | 이렇게 됩니다' 표 → 상태 · 권한 · 결정표 → 미정 질문 → 이어지는 영역.
- 맨 앞 '전체 지도'(영역이 이어지는 순서 · 등장인물 · 용어 · 그림 읽는 법), 맨 끝 '관련 문서에서 볼 곳'(기능 ID는 여기에만).
- 본문에 버전 · 기능 ID를 쓰지 않는다. 화면 문구 · 입력 형식 · 칸 목록 같은 기능 세부는 넣지 않는다.
- 공식 문서로 쓰면 본문 말투를 하나로(예: 합니다체) 정하고, 그림 · 따옴표 안 화면 문구는 화면 말투 그대로 둔다. 맨 위 문서 정보 칸(문서명 · 버전 · 작성일 · 작성 · 적용 범위 · 공개 범위).
- 흐름 그림은 Mermaid. 여러 주체가 주고받으면 sequenceDiagram, 상태는 stateDiagram. 칸 글자를 '1. '처럼 숫자+점으로 시작하지 않는다. 문법과 실제 그리기 둘 다 검사한다.
- 원본 파일을 고치면 공유 페이지(HTML)를 다시 만들어 **같은 링크**에 올린다. 올리기 전 검사: 표 칸 수 · 말투 섞임 0 · 그림 오류 0 · 기능정의서와 미정 번호 일치. 원본 위치 · 만드는 명령 · 링크는 프로젝트 폴더의 `planning-config.md` › '정책' 절.
- **뺀 기능은 본문에 '없음 · 1차 제외'로 남기지 않는다.** 그 기능을 전제로 한 문장을 지우고 남은 규칙만 쓴다(10절). 흔적은 기능정의서 변경 기록 · 후속 고려 탭에만.
- 기능정의서 미정을 바꾸면 정책 미정 표도 같은 작업 안에서 맞춘다(`spec-sheet-writing` 9절).

- [ ] 목차가 돈 → 법 → 핵심 흐름 → 예외 → 운영 순인가
- [ ] 규칙마다 한 문장·선언형이고, 주어와 숫자가 분명한가
- [ ] 조건이 얽힌 규칙은 결정표로 썼는가
- [ ] 화면 문구·입력 형식·번호 형식 같은 기능명세 세부가 본문에 없는가
- [ ] 개념·계산·기간·예외 규칙에 숫자가 든 예시가 있는가
- [ ] 8절 점검표의 주제를 모두 확인했는가 (정함 / 해당 없음 / 미정)
- [ ] 미정 사항이 질문 목록에 번호·가정값과 함께 있는가
- [ ] 범위에서 뺀 기능을 전제로 한 문장이 남아 있지 않은가
- [ ] 다시 읽어 확인했고 변경 이력을 남겼는가
