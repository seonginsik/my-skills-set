# 기능정의서 작성 스킬 (표 형태 문서 — 엑셀 · 구글 시트 기본, 노션 데이터베이스 포함)

> 이 파일은 `spec-sheet-writing` 스킬입니다.
> 기능정의서를 새로 쓰거나, 고치거나, 기능을 범위에서 빼거나, 미정 질문을 관리할 때 이 파일을 먼저 읽고 따른다.
> 도메인 · 프로젝트와 관계없이 쓴다. **기본은 스프레드시트(엑셀 · 구글 시트)**이고, 빈 문서로 새로 시작할 때(0-2절)와 노션 데이터베이스로 쓸 때(0-1절)에도 같은 규칙을 적용한다.
> 프로젝트마다 다른 값(문서 위치 · 탭 번호 · 기능 ID 접두어 · 용어 · 도구 명령 · 보안 규칙)은 **프로젝트 폴더의 `planning-config.md` › '기능정의서'** 절에서 찾는다. 이 스킬에는 고유 이름을 적지 않는다. 설정 파일이 없으면 0-2절 순서로 만든다.
> 같이 쓰는 스킬: 단계 순서 `product-planning-process` · 정책 문장 `policy-doc-writing` · 화면설계 `screen-spec-writing` · 문구 `ux-writing`

## 0-1. 도구별로 바꿔 끼우기

아래 본문은 스프레드시트 용어(탭 · 줄 · 칸 · 셀 메모)로 쓴다. 다른 도구면 이 표대로 바꿔 읽는다. 규칙(무엇을 담고, 언제 무엇을 기록하나)은 같다.

| 본문 용어 | 엑셀 파일 | 구글 시트 | 노션 데이터베이스 |
|---|---|---|---|
| 문서 | 파일 하나 | 스프레드시트 하나 | 상위 페이지 하나 + 그 안의 데이터베이스들 |
| 탭 | 시트 | 시트(고유 번호 gid로 찾음) | 데이터베이스(또는 같은 DB의 보기) — 데이터 소스 ID로 찾음 |
| 줄 · 칸 | 행 · 셀 | 행 · 셀 | 행(페이지) · 속성 |
| 영역 구분 줄 | 짙은 색 구분 행 | 짙은 색 구분 행 | '영역' 선택 속성 + 보기에서 영역으로 묶기 |
| 줄 색(5절) | 행 배경색 | 행 배경색 | '구분' 선택 속성(그대로 · 고침 · 후속 · 새로, 선택지 색을 범례와 같게) |
| 셀 메모(6절) | 셀 메모 | 셀 메모 | 그 행 페이지 본문 맨 아래 '이력' 줄(또는 '변경 메모' 속성) |
| 변경 기록 탭 | '변경 기록' 시트 | '변경 기록' 시트 | '변경 기록' 데이터베이스(기능 행과 관계형 연결) |
| 후속 고려 탭(7절) | '후속 고려' 시트로 행 옮김 | 같음 | '개발 단계 = 후속'으로 바꾸고 '후속 고려' 보기에만 보이게(행은 옮기지 않음) |
| 화면설계 칸(8절) | 하이퍼링크 셀 | 조각 링크 셀 | 글 속성에 링크(화면 ID마다) 또는 URL 속성 |
| 미정사항 탭(9절) | '미정사항' 시트 | 같음 | '미정' 데이터베이스(관련 기능과 관계형 연결) |
| 미리 보기 → 쓰기(6절) | 바꿀 행 · 값 목록을 먼저 보여주고 쓴다 | 도구의 미리 보기 | 바꿀 행 · 속성 목록을 먼저 보여주고 쓴다 |

- 엑셀 파일은 버전 기록이 약하다. 파일을 덮어쓰기 전에 사본을 남기거나(보안 규칙이 허락하면) 저장소에서 관리하고, 변경 기록 시트를 꼭 쓴다.
- 노션은 행마다 페이지가 있으니 긴 동작 설명은 속성 대신 페이지 본문에 써도 된다. 그때도 칸 구분(동작 · 예외 · 저장 · 비고)은 본문 제목으로 지킨다.

## 0-2. 빈 문서로 새로 시작할 때

1. **설정 파일부터:** 프로젝트 폴더에 `planning-config.md` › '기능정의서' 절을 만든다 — 도구 · 문서 위치 · 보안 규칙 · 기능 ID 접두어 · 주체(사용자 종류) · 용어집 위치.
2. **원본이 있는지 확인:** 회사 원본 기능정의서 · 요구사항이 있으면 그 열 구성과 메뉴를 출발점으로 쓰고, 원본 파일은 고치지 않는다(새 문서로 옮김). 원본 행을 옮길 때 줄 색으로 그대로 · 고침 · 후속 · 새로를 구분한다.
3. **뼈대 만들기:** 2절 탭 구성, 3절 열 구성, 5절 줄 색 범례를 커버에 적고, 변경 기록 · 후속 고려 · 미정사항 탭을 빈 채로 만든다.
4. **견본 한 영역:** 한 영역(도메인)을 먼저 채워 보여주고 OK를 받은 뒤 나머지를 채운다.
5. 설정 파일에 탭 번호(또는 데이터베이스 ID)를 적는다.

## 1. 기능정의서가 담는 것 · 담지 않는 것

| 담는다 | 담지 않는다 (정책 문서로) |
|---|---|
| 화면 · 기능 하나마다 동작 · 예외 · 저장 데이터 | 상태표 · 결정표(숫자 예시) · 권한표 |
| 미정 질문 (별도 탭) | 변경 대조표 · 문서 변경 이력 |
| 화면설계로 가는 링크 | 흐름 그림 |

- **규칙은 정책 문서에서 내려온다.** 기능정의서에서 새 규칙을 만들지 않는다. 새 규칙이 필요하면 정책 문서에 먼저 쓰고 내려온다. 기능정의서가 정책의 표를 가리킬 때는 정책 절 번호로 쓴다(예: '운영정책 4.6 「환불 결정표」').
- 기능정의서는 **1차에 만들 것만** 담는다. 후속 기능은 '후속 고려' 탭에 둔다(7절).

## 2. 탭 구성 (기본)

| 탭 | 내용 |
|---|---|
| 커버 | 문서 이름 · 줄 색 범례 · 읽는 법 |
| 변경 기록 | 제품 기능의 추가 · 수정 · 삭제만 (6절) |
| IA 요약 · 메뉴구조 | 주체(사용자 · 판매자 · 운영자 등)별 메뉴 트리, 1차/후속 |
| 기능정의서 | 주체별 탭. 영역(도메인)마다 짙은 색 영역 구분 줄 |
| 후속 고려 | 범위에서 뺀 기능 줄 (7절) |
| 미정사항 | 미정 질문 (9절) |

- 탭은 이름이 아니라 **고유 번호**(시트 gid · 데이터베이스 ID)로 찾는다. 사람이 탭 이름을 바꿔도 도구가 동작하게.

## 3. 열 구성과 기능 ID

기본 열: `기능 ID · 메뉴 노출 · Depth 1(대메뉴) · Depth 2(중메뉴) · Depth 3(화면/탭) · Depth 4(영역/팝업) · 기능명 · 동작 상세 및 비즈니스 로직 · 예외 처리 · 저장 데이터 · 비고 · 개발 단계 · 화면설계`

- 회사 원본 양식이 있으면 그 열을 그대로 쓴다. 원본 파일은 고치지 않고 새 문서로 옮긴다.
- **기능 ID** = `접두어-영역-번호`. 번호는 5 간격(010 · 015 · 020)으로 매겨 사이에 끼워 넣을 자리를 둔다. 한 번 쓴 번호는 다른 기능에 다시 쓰지 않는다.
- 시스템이 혼자 처리하는 기능(배치 · 기록 등)은 Depth 3 · 4에 `(시스템)`.

## 4. 칸 쓰는 법

| 칸 | 쓰는 법 |
|---|---|
| 기능명 | 무엇을 하는지 명사구 하나 (예: '로그인 이메일 등록 및 인증') |
| 동작 상세 | `- ` 한 줄에 규칙 하나, 선언형(~한다 / ~할 수 없다). 숫자 · 기한은 숫자로. 헷갈리는 규칙 밑에 들여쓴 `예:` 한 줄 |
| 예외 처리 | 입력 오류 · 중복 · 동시 처리 · 외부 연동 실패 · 기한 지남 · 권한 없음을 빠짐없이. 무엇을 막고 무엇을 안내하는지 |
| 저장 데이터 | 이 기능이 남기는 값 목록. 비밀번호 · 인증코드 원문은 '저장하지 않음'을 적는다 |
| 비고 | 근거(법 조항 · 정책 절), 원본에서 바뀐 점, AI가 스스로 정한 '판단한 곳' |
| 개발 단계 | 1차 / 후속 |
| 화면설계 | 화면 ID + 화면설계 링크 (8절) |

- **시니어 수준으로 채운다:** 해당 업종 법 · 개인정보 보호 기준, 예외, 동시 처리, 기한을 넣는다.
- **용어는 하나로:** 프로젝트 용어집(설정 파일)에 있는 말만 쓴다. 같은 대상을 여러 이름으로 부르지 않는다.
- **화면 문구**는 `ux-writing` 스킬과 프로젝트 문구 가이드를 따른다(주체마다 말투가 다를 수 있음).
- **본문에 쓰지 않는 문장:** "~는 후속이다", "1차에는 없다 / 제공하지 않는다", "(○○ 제외)". 정책에 후속으로 적혀 있어도 기능정의서 본문에서는 지운다. 남은 기능만 설명한다.

## 5. 줄 색 범례

| 색 | 뜻 |
|---|---|
| 흰색 | 원문 그대로 (원본이 없는 탭은 처음 쓴 줄이 흰색) |
| 하늘색 | 1차 기준으로 고침 |
| 회색 | 원문 보존, 후속 |
| 노란색 | 새로 추가 |

## 6. 고치는 법 · 이력

**고치는 법**
1. 시트를 통째로 다시 쓰지 않는다. **고칠 줄 · 칸만** 고친다.
2. 고칠 목록을 만든 뒤 **미리 보기**로 바뀔 칸을 확인하고 쓴다. 바꿀 글이 그 칸에 정확히 한 번 있는지 먼저 검사한다.
3. 문서 내용이 대외비면 PC에 사본을 남기지 않는다. 고칠 목록은 임시 폴더에 두고 끝나면 지운다(설정 파일의 보안 규칙을 따른다).
4. 쓴 뒤 문서를 다시 읽어 확인한다.

**셀 메모** — 제품 기능을 더하거나 고치거나 뺀 칸에만 한 줄 덧붙인다. 기존 메모는 지우지 않는다.
- 형식: `YYYY-MM-DD 추가|수정: 무엇을 어떻게 (근거)`
- 메모하지 않는 것: 링크 · 칸 제목 · 용어 통일 · 서식 · 색 · 미정 등급

**변경 기록 탭** — 제품 기능의 추가 · 수정 · 삭제만 한 줄씩, 최신이 위.
- 칸: 날짜 · 구분(추가/수정/삭제) · 시트 · 영역 · 기능 ID · 항목 · 무엇이 바뀌었나 · 바로 가기
- '무엇이 바뀌었나'는 처음 보는 사람이 읽게 '무엇을 어떻게 (근거)'로.
- 같은 날 같은 내용이면 한 줄로 합치고 기능 ID · 항목만 이어 적는다.
- 쓰지 않는 것: 링크 채우기 · 칸 제목 · 용어 통일 · 서식 · 메모만 · 미정 등급 · 메뉴구조 정리. 실수로 쓴 줄은 지운다.
- 여럿이 쓰면 작성자 칸을 둔다(`team-collaboration-process`).

## 7. 기능을 범위에서 뺄 때

1. 정책 문서에서 먼저 뺀다(`policy-doc-writing` 10절).
2. 기능 줄은 지우지 않고 **'후속 고려' 탭 끝으로 옮긴다.** 값 · 서식 · 메모 · 링크를 그대로 두고 줄 색은 회색. 탭이 비어 있으면 기능정의서 머리글 · 열 너비부터 깐다.
3. 변경 기록에 '삭제 — 후속 고려 탭으로 옮김 (근거)' 한 줄.
4. 그 기능 ID나 기능을 언급하던 **다른 줄의 문장을 정리**한다. 고쳐 쓰지 말고 그 문장을 지워 남은 기능만 설명한다. 대신 사용자가 어디서 무엇을 하게 되는지는 남긴다.
5. 법 기준 때문에 넣었던 기능을 빼면 확인 질문을 미정에 남긴다.

## 8. 화면설계 칸

- 줄을 새로 쓰거나 고칠 때마다 '화면설계' 칸에 **화면 ID + 그 화면 첫 상태 장 링크**를 함께 넣는다. 화면 ID마다 링크를 따로 건다.
- 링크는 화면 ID ↔ 노드 대응표(설정 파일 경로)에서 찾는다. 새 화면이라 대응표에 없으면 비워 두고 화면설계 담당에게 대응표 갱신을 부탁한다.
- 화면 없이 시스템이 처리하는 기능은 비워 둔다. 화면을 보관 구역으로 옮기면 걸린 칸의 링크를 지운다(후속 고려 탭의 줄은 그대로).

## 9. 미정사항 탭

- 칸: 영역 · 번호 · 질문 · 가정값(현재 설계 기준) · 1차 영향(🔴 막음 / 🟠 개발 중 필요) · 확인 부서 · 상태(미확인 · 확인 중 · 결정됨) · 관련 기능 ID
- **가정값은 꼭 쓴다.** 본문은 가정값대로 써 두고, 결정되면 바꾼다.
- **후속으로 미뤄도 되는 질문은 넣지 않는다.** 나중에 보완이 필요하면 제안만 한다.
- 결정되면: 정책 → 기능정의서 본문을 결정값으로 고치고, 미정 줄을 지운다. 본문의 '미정 · 번호' 표시도 지운다.
- **정책 문서의 미정 표와 번호를 늘 맞춘다.** 시트 미정을 바꾸면 같은 작업 안에서 정책 미정 표도 묻지 않고 맞추고, 대조 도구로 '번호 일치 · 참조 끊김 없음'을 확인한다. 문장은 정책 쪽이 쉬운 말이라 같지 않아도 되지만 번호 · 가정값 뜻 · 1차 영향은 같아야 한다.
- 영역 칸은 영역마다 정해진 연한 색으로 구분한다.
